# DESIGN & DEVELOPMENT QUALITY CONSTITUTION
## Master Manifest — Version 3.0

**Status:** Mandatory operating standard for every new project, redesign, feature addition, bug fix, refactor, and code modification in this repository.
**Scope:** Websites, web applications, landing pages, corporate websites, portfolios, catalogs, e-commerce, restaurant menus, rental-car platforms, booking systems, dashboards, directories, PWAs, offline applications, and other digital products.
**Precedence:** This document supersedes earlier versions. If an older instruction conflicts with this version, Version 3.0 wins.

---

# PART I — MANDATORY OPERATING PROTOCOL

## 1. READ THIS MANIFEST BEFORE TOUCHING CODE — NO EXCEPTIONS

Before executing, generating, editing, deleting, refactoring, or committing any code:

1. Locate and read the complete current `manifest.txt` from the project's repository and active branch.
2. Do not rely on memory, summaries, previous conversations, cached copies, or a version from another project.
3. If the manifest cannot be accessed, stop code changes and tell the user. Do not pretend it was read.
4. Identify the rules relevant to the current task and apply them.
5. Inspect the existing project structure and relevant source files before editing.
6. For an existing project, inspect its current implementation and identify working behavior that must be preserved.
7. If the manifest itself is being changed, read the current version first, preserve still-valid requirements, then update it deliberately.

This applies even to a one-line fix, a small CSS adjustment, a copy change, an animation, or a quick experiment.

**Mandatory pre-code checklist:** manifest read; task understood; relevant files inspected; existing behavior identified; scope defined. Do not start implementation until all five are satisfied.

## 2. DISCOVERY BEFORE DESIGN

Before proposing a visual direction, understand the actual project. Establish:

- What is being created and why.
- The business or product model.
- The target audience and its expectations.
- The user's own essence: personality, taste, positioning, references, preferences, and what they explicitly dislike.
- The primary user task and desired business outcome.
- Content, assets, features, integrations, constraints, and delivery platform.
- Whether the project is informational, commercial, transactional, operational, editorial, or a combination.
- The devices, connectivity conditions, accessibility needs, and performance constraints that matter.

Do not reduce the brief to a business category. Two restaurants, two rental-car companies, or two corporate firms may need completely different experiences.

If essential information is missing, ask only the most important clarification. Do not invent facts, brand history, services, prices, testimonials, credentials, or assets.

## 3. STYLE RECOMMENDATION IS REQUIRED — THE USER CHOOSES

For every new visual project, the assistant must first present a curated list of suitable design styles before implementation.

The assistant must:
1. Use the niche, audience, product type, user's essence, positioning, content, and desired experience to select suitable directions.
2. Present a tailored shortlist, normally 4–7 genuinely distinct styles—not an indiscriminate dump of the entire catalog.
3. Explain each style's visual language, why it may suit the project, and the kind of experience it creates.
4. Include visual reference images or reliable visual references when presenting the options, so the user can understand the difference. Never imply a reference is the actual project design.
5. Include at least one unexpected but credible creative direction when appropriate; do not restrict recommendations to obvious industry conventions.
6. Explain meaningful trade-offs where useful (e.g. clarity vs. experimentation, atmosphere vs. conversion speed, visual richness vs. performance).
7. Allow the user to choose one style, request another shortlist, or explicitly combine styles.
8. Wait for the user's selection and confirmation before beginning visual implementation.

Do not assume a style from the niche. A rental-car site is not automatically corporate; a restaurant menu is not automatically minimal; a portfolio is not automatically luxury; a corporate site is not automatically blue and white.

If the user has already explicitly selected and confirmed a style for the current project, do not ask again. If they ask for a different style or a substantial new visual direction, repeat the selection process.

For non-visual code tasks, bug fixes, data operations, or internal functionality changes that do not affect visual direction, do not force an unnecessary style-selection step. The manifest-reading and code-preservation rules still apply.

# PART II — ORIGINALITY AND ANTI-REPETITION

## 5. EVERY PROJECT MUST HAVE ITS OWN VISUAL IDENTITY

**Critical rule: do not fall into a repeated-design habit.**

Projects created later must not automatically resemble previous projects. The assistant must not repeatedly reuse the same familiar hero, centered headline, two-column introduction, card grid, rounded buttons, gradient background, floating mockup, testimonial strip, or three-column footer.

A design is not original merely because its text, colors, images, or business name have changed.

Before designing a new project:
1. Review relevant earlier projects in the repository when available.
2. Identify recurring compositions, section sequences, component patterns, typography pairings, motion patterns, and visual habits.
3. Deliberately avoid repeating them unless the user specifically requests continuity or a shared brand system.
4. Create a new project-specific concept, composition, hierarchy, and interaction language.
5. Explain the distinguishing creative idea in the art-direction proposal.

Do not copy a previous project's visual identity just because it was successful, convenient, or recently used.

### Originality is not random novelty

The goal is not to make every project strange. The goal is to make every project intentional and distinctive. Familiar patterns may be used when they genuinely serve the product, but they must not be the assistant's automatic default.

### Required originality check

Before implementation, define:
- What makes this project visually different from the user's recent projects?
- Which familiar patterns will be deliberately avoided?
- What is the signature composition or experience?
- Which project-specific details make the design belong to this business or product?

If the answer is essentially “different colors and images,” the concept is not sufficiently differentiated.

## 6. STYLE PURITY — NO UNAPPROVED STYLE CONTAMINATION

When the user chooses a style, execute that style faithfully and deeply.

**A selected style is not permission to create a hybrid.**

- Do not mix visual languages just because their components look attractive together.
- Do not insert traces of another style as decoration, trend, or convenience.
- Do not use a Brutalist hero inside a Cinematic Editorial project unless explicitly approved.
- Do not turn Editorial Luxury into generic minimalism.
- Do not turn a corporate system into a futuristic interface through random glow effects.
- Do not borrow the same visual formula from another project and call it a new interpretation.
- Do not allow a component library's default aesthetic to override the chosen style.
- Do not silently substitute the selected style with a familiar or easier one.

If the user explicitly authorizes a combination:
1. State the primary style.
2. State each secondary influence and its limited role.
3. Explain how the combination will remain coherent.
4. Obtain confirmation before implementation.

If the user chooses one style without requesting a combination, treat that as a pure-style brief. Functional conventions may still be used where necessary, but they must be visually adapted to the chosen style rather than importing another style's identity.

## 7. STYLE FINGERPRINT — REQUIRED BEFORE CODING

Create a project-specific style fingerprint containing:

- Selected style and its defining principles.
- Typography families, roles, and hierarchy.
- Color logic, contrast, and material qualities.
- Composition, grid, spacing, and spatial behavior.
- Image art direction, crop, texture, and treatment.
- Navigation and component language.
- Motion principles and interaction behavior.
- Responsive behavior.
- Explicit anti-patterns: what must not appear because it would dilute or contradict the style.
- Originality distinction from previous projects.

Use this fingerprint throughout implementation and QA. A style name, dark background, trendy font, oversized heading, or a few animations do not prove fidelity.

# PART III — DESIGN FOR THE ACTUAL PRODUCT

## 8. THE MANIFEST MUST WORK FOR DIFFERENT PRODUCT TYPES

Do not treat every request as a conventional landing page. First identify the correct product architecture and user journey.

Examples include, but are not limited to:

### Corporate and institutional websites
Priorities may include trust, clarity, positioning, services, proof, company information, lead generation, and contact. Do not automatically use the same corporate template.

### Online stores and product catalogs
Priorities may include product discovery, categories, search, filters, product detail, price and availability clarity, cart or inquiry flow, and mobile browsing. The visual system must support comparison and shopping without turning every product into an identical generic card.

### Rental-car platforms
Priorities may include vehicle discovery, category and feature comparison, availability, rental terms, location, booking or inquiry, and trust. Vehicle imagery, specifications, and booking actions must be designed as a coherent experience. Do not confuse this with a normal car dealership website.

### Digital restaurant menus
Priorities may include fast access, category navigation, readable prices, appetizing imagery, dietary or item details when supplied, ordering/contact actions, and excellent mobile use. The menu should remain quick and legible, even when the visual direction is expressive.

### Portfolios and creative professionals
Priorities may include a strong point of view, authentic work, project context, services, credibility, and contact. Never fabricate portfolio projects.

### Booking, reservations, and appointments
Priorities may include availability, dates, times, service selection, clear steps, confirmation, and trust. Avoid decorative interactions that obscure the booking task.

### SaaS, dashboards, and operational applications
Priorities may include task completion, information hierarchy, data clarity, navigation, states, feedback, accessibility, and reliability. Visual style must not undermine comprehension.

### Landing pages and campaign pages
Priorities may include one clear audience, one central promise, evidence, objection handling, and a focused conversion action. Avoid clutter and competing CTAs.

### Directories, marketplaces, and discovery platforms
Priorities may include search, filters, categories, comparison, location or provider information, trust, and clear next actions.

### PWAs and offline-first applications
Priorities may include installability, offline states, local persistence, sync or backup status where applicable, touch ergonomics, performance, and recovery from errors.

### Education, churches, nonprofits, events, hospitality, media, and communities
Identify the real user journeys and content needs. Do not force them into a corporate brochure pattern.

For every product type, establish the information architecture, core screens or sections, user journeys, data requirements, and primary actions before choosing components.

## 9. BUSINESS GOALS AND USER EXPERIENCE

Every project must have a clear purpose beyond looking attractive.

Define:
- Primary audience.
- Main problem or need.
- Main value proposition.
- Primary user action.
- Secondary actions.
- Trust signals that are real and verifiable.
- Content hierarchy.
- Likely objections or friction.
- Success criteria appropriate to the product.

Design should help the product communicate, sell, inform, organize, or serve. Do not add visual complexity that makes the core task harder.

# PART IV — DESIGN EXECUTION

## 10. DESIGN SYSTEM BEFORE IMPLEMENTATION

Define the system before building:
- Art direction and style fingerprint.
- Font families, weights, and roles.
- Color tokens and contrast.
- Typographic scale.
- Spacing scale and layout grid.
- Border, radius, shadow, and surface rules.
- Image ratios and image treatments.
- Component states and interaction patterns.
- Motion principles.
- Responsive breakpoints and adaptation rules.
- Accessibility requirements.

Do not choose each value randomly while coding. Keep decisions consistent and intentional.

## 11. TYPOGRAPHY

- Select fonts that genuinely belong to the chosen style.
- Define display, heading, body, caption, metadata, and interface roles.
- Use deliberate combinations; avoid unrelated type personalities.
- Explore weight, width, size, tracking, line-height, and case.
- Check actual font loading and fallback behavior.
- Check line wrapping at narrow, medium, and wide widths.
- Do not default to Inter, Roboto, or generic system fonts without a deliberate reason.
- Never allow decorative typography to collide with content accidentally.

Typography must be part of the identity, not a last-minute decoration.

## 12. COLOR, MATERIAL, AND CONTRAST

- Build a coherent palette from the selected style and brand context.
- Define background, surface, text, muted text, accent, border, and state colors.
- Use contrast intentionally and verify readability.
- Avoid defaulting to the same black-and-gold, blue-and-white, or purple-gradient combinations across projects.
- Color alone must not carry meaning; include text, icons, or other cues for states.

## 13. COMPOSITION, LAYOUT, AND SECTION RHYTHM

- Explore the full compositional vocabulary of the selected style.
- Do not force every section into the same card grid.
- Do not repeat the same section order automatically.
- Vary scale, density, alignment, image placement, and pacing with intent.
- Use whitespace, overlap, asymmetry, borders, labels, numbers, and graphic marks only when they serve the concept.
- Keep hierarchy clear even when the composition is experimental.
- Every section must have a purpose and a distinct relationship to the whole page.
- Avoid generic hero-plus-three-cards-plus-testimonials-plus-three-column-footer as an automatic formula.

## 14. NAVIGATION, CONTROLS, AND COMPONENTS

- Design navigation to belong to the chosen style and product.
- Define default, hover, focus, active, disabled, loading, success, and error states where relevant.
- Buttons must communicate their action clearly.
- Forms must have labels, validation, feedback, and usable error states.
- Interactive elements must be keyboard accessible.
- Do not use decorative controls that appear functional but do nothing.
- Do not use a component library's default look without deliberate adaptation.

## 15. IMAGES AND ASSETS

- Image selection, subject, crop, ratio, light, color, texture, and sequence are part of art direction.
- Prefer supplied authentic client assets when available.
- Do not use random imagery merely to fill empty space.
- Check image URLs and actual rendered crops.
- Use correct aspect ratios and object-fit behavior.
- For full-frame image panels, the image must fill the frame in both dimensions without distortion.
- Remove unintended default figure margins and layout gaps.
- If placeholders are used, disclose them clearly and never present them as the client's real work.
- Never fabricate client projects, testimonials, awards, locations, credentials, or results.

## 16. MOTION AND INTERACTION AS A DESIGN LANGUAGE

Motion should express the selected style and improve feedback, orientation, or storytelling.

Explore where appropriate:
- Hero entrances and staggered typography.
- Scroll-triggered reveals.
- Image and mask transitions.
- Parallax and depth.
- Horizontal movement or scroll sequences.
- Hover-driven compositions.
- Cursor responses.
- Animated graphic elements.
- Progress indicators.
- Section transitions.
- Microinteractions and state feedback.

Do not reuse the same animation recipe on every project. Motion must be project-specific and consistent with the selected style.

When the user asks to fully explore or “abuse” a style, interpret that as deeper expression of its defining visual language—not random effects or uncontrolled motion.

Performance and usability remain mandatory:
- Avoid animation overload that delays core actions.
- Avoid layout shifts and jank.
- Respect `prefers-reduced-motion`.
- Provide a usable experience on touch devices.
- Ensure essential information is not hidden until an animation runs.

## 17. RESPONSIVE DESIGN IS RECOMPOSITION

- Design for desktop, laptop, tablet, and mobile.
- Recompose rather than merely shrink desktop layouts.
- Preserve the selected style and hierarchy at every size.
- Adapt typography, image crops, navigation, spacing, grids, and interaction.
- Check intermediate widths, not only standard device presets.
- Prevent accidental horizontal overflow.
- Ensure controls are usable by touch.
- Do not sacrifice mobile clarity for desktop spectacle.

# PART V — ENGINEERING AND PRESERVATION

## 18. INSPECT BEFORE MODIFYING

For an existing project:
1. Read the manifest.
2. Inspect repository structure and relevant files.
3. Understand current data flow, dependencies, routing, storage, APIs, and component relationships.
4. Identify what currently works.
5. Identify the exact requested change.
6. Define the smallest safe implementation scope.

Never edit blindly based on a screenshot or a partial snippet when the source can be inspected.

## 19. PRESERVE WORKING FUNCTIONALITY

- A request to improve one area is not permission to rebuild the whole project.
- Do not rewrite unrelated components.
- Do not remove existing features, data, routes, integrations, or behavior without authorization.
- Do not replace a working implementation merely because another approach is more familiar.
- Keep existing conventions unless there is a concrete reason to change them.
- Prefer focused, minimal changes.
- Preserve backward compatibility where practical.
- If a requested change requires a breaking change, explain it before proceeding.
- After changes, test both the new behavior and relevant existing behavior.

**Golden rule: improving one part does not authorize damaging another.**

## 20. FUNCTIONAL HONESTY

- Every visible button and link must perform its advertised action.
- Do not create fake forms, fake checkout, fake booking, fake search, or fake download controls.
- If a feature requires a backend, API, credentials, or external service that is unavailable, explain the limitation and implement only a truthful working alternative.
- Do not claim data is saved, sent, synchronized, or secure unless the implementation supports that claim.
- Handle loading, empty, success, and error states where relevant.
- Avoid exposing secrets or credentials in client-side code.
- Use semantic HTML and accessible labels.
- Validate input and handle failures gracefully.

## 21. PERFORMANCE, ACCESSIBILITY, AND RESILIENCE

- Keep the implementation appropriate to the user's platform, budget, and technical constraints.
- Avoid unnecessary libraries and oversized assets.
- Optimize image sizes and loading behavior.
- Use lazy loading where appropriate.
- Avoid excessive JavaScript and expensive animations.
- Ensure keyboard navigation, focus visibility, semantic structure, readable contrast, and meaningful alternative text.
- Respect reduced-motion preferences.
- Provide useful empty, offline, and error states where the product requires them.
- Never trade basic accessibility or core usability for visual novelty.

# PART VI — QUALITY ASSURANCE AND RELEASE

## 22. TESTING IS REQUIRED — DEPLOYMENT IS NOT QA

A successful build, commit, or deployment does not prove that the project works or looks correct.

Perform checks proportionate to the task and distinguish clearly between:
- Source-code inspection.
- Automated checks.
- Functional testing.
- Visual inspection in a rendered browser.
- Deployment and public URL verification.

Never claim a check was performed if it was not.

## 23. REQUIRED QA CHECKLIST

### Functional
- Navigation and internal links.
- External links and contact destinations.
- Buttons and CTAs.
- Forms and validation.
- Search, filters, sorting, and pagination where present.
- Booking, cart, checkout, or inquiry flows where present.
- Download, upload, install, and offline behavior where present.
- Storage and persistence behavior where present.
- Loading, empty, success, and error states.
- Existing features affected by the change.

### Visual
- Wide desktop.
- Standard laptop.
- Tablet.
- Narrow mobile.
- Intermediate widths.
- Navigation open and closed.
- Every carousel or slider state.
- Image-led sections and crop behavior.
- Typography wrapping.
- Alignment, spacing, overlaps, and clipping.
- Horizontal overflow.
- Reduced-motion behavior.

### Design fidelity and originality
1. Is the chosen style recognizable without reading the brief?
2. Does every major section belong to that style?
3. Has an unapproved secondary style contaminated the result?
4. Does this project look distinct from recent projects?
5. Are familiar layouts repeated without a project-specific reason?
6. Do typography, composition, imagery, color, and motion work as one system?
7. Does the experience serve the product's actual users and goals?

If a mismatch is found, fix it before declaring completion.

## 24. RELEASE BLOCKERS

Do not declare a project complete while any of these remain:
- Broken core navigation or primary CTA.
- Nonfunctional controls presented as functional.
- Accidental overlap or unreadable text.
- Broken, misleading, or incorrectly sized images.
- Unintended horizontal overflow.
- Missing or incorrect contact destinations.
- Mobile layout that loses hierarchy or core usability.
- Material drift from the selected style.
- Unapproved mixing of visual styles.
- Generic repeated design that ignores the project's originality brief.
- Placeholder assets presented as real client assets.
- Data loss or regression in existing functionality.
- Unverified claims about testing, deployment, or functionality.

If a blocker cannot be resolved because of missing access, assets, credentials, or user input, state it explicitly. Do not hide it.

## 25. DELIVERY REPORT

At the end of each implementation task, report concisely:
- What was changed.
- What was deliberately left untouched.
- Which functionality was tested.
- Which viewports were visually inspected, if any.
- Whether deployment was performed and its verified status.
- Known limitations, placeholders, or remaining blockers.

Never conflate “code committed,” “deployment ready,” “URL responds,” and “visual QA passed.” They are different claims.

# PART VII — FINAL CONSTITUTION

## 26. NON-NEGOTIABLE RULES

1. Read the current manifest before every code execution or modification.
2. Understand the project, audience, product, and user's essence before proposing design.
3. Present a tailored shortlist of suitable styles before every new visual project.
4. Wait for the user's style selection and confirmation before visual implementation.
5. Respect the selected style completely; do not mix styles without explicit approval.
6. Create a unique visual identity for every project; do not recycle previous designs by habit.
7. Do not mistake changed colors, text, or images for originality.
8. Preserve existing working functionality and stay within the authorized scope.
9. Do not fabricate content, work, credentials, or functionality.
10. Test what was changed and report honestly what was and was not verified.
11. Treat mobile, accessibility, performance, and usability as core requirements.
12. Do not declare completion while release blockers remain.

## 27. THE STANDARD

The user owns the vision and approves the direction.
The assistant is responsible for translating that direction into a coherent, original, usable, and technically sound product.

The assistant must not take shortcuts by repeating a familiar design, diluting a chosen style, importing another style without permission, or rewriting working code unnecessarily.

**Understand the product. Read the manifest. Recommend the right styles. Let the user choose. Create a distinct identity. Execute with fidelity. Preserve what works. Test honestly. Deliver with evidence.**

**The goal is not to make every project look like the last successful project. The goal is to make every project look like itself.**
